## Context

Four independent asks landed in the same conversation, all extending the `post-service-messaging` capability area (`RosterMember`, `MessageTemplate`, `MessageRule`, `MessageLog`, `ServiceTime`, `BirthdayMessageSetting` — see `openspec/changes/post-service-messaging/`). `WhatsAppServiceClient` (the single choke point for every outbound WhatsApp call) was just hardened this session to normalize Brazilian phone numbers — that fix is stable and out of scope here; nothing in this change touches it.

Current state, precisely:
- Manual send (`messageAdapters.ts`'s `sendNow` → `dispatchMessageSend`) resolves recipients by `statusesForAudience(audience)` where `audience` is `VISITOR | MEMBER | ALL`, always live off `RosterMember.status` at send time.
- Automatic rules (`messageRuleScheduler.ts`) tick every 60s, compute `serviceTime.time + offsetMinutes` as the target fire time, and fire once per week's occurrence via `lastFiredAt`.
- Birthday checks (`birthdayScheduler.ts`) tick every 60s but no-op before a single hardcoded `NOTIFY_HOUR = 8`, global for every church, checked *before* the per-church loop even starts.
- `ServiceAttendance` (built the same session as the admin-nav redesign, per this repo's recent history) is one row per `serviceTimeId` + `date`, holding aggregate `visitorCount`/`memberCount` — no time-of-day field at all today.
- The admin hub's "Membros" stat card (`admin/index.vue`) counts `useMembers()` — i.e. `ChurchMembership` rows (people with app logins) — which is a **different number** from `RosterMember` counts (visitors/members tracked for outreach, login optional). This is called out explicitly because it's the most likely point of confusion for capability #2.

## Goals / Non-Goals

**Goals:**
- Let a pastor send to an explicit hand-picked list of roster members, mixing visitor and member status freely.
- Show, at a glance, how many active visitors vs. members are in the roster.
- Let each church pick its own birthday-notification time instead of a fixed 8am for everyone.
- Let automatic message rules fire off when a service *actually* ended, when a pastor bothers to record that, instead of always trusting the scheduled time.

**Non-Goals:**
- Not building a full "culto occurrence" tracking system (start time, attendance-taking workflow, multi-session cultos) — `manual-service-end-trigger` is one timestamp on the existing `ServiceAttendance` row for today, nothing more.
- Not making `MessageRule` itself target selected recipients — rules are recurring and audience-agnostic-of-individuals by design (see `post-service-messaging`'s own "audience computed live, not a saved list" decision); `SELECTED` is a manual-send-only audience value.
- Not changing how `VISITOR`/`MEMBER`/`ALL` audiences behave — fully additive.
- Not adding delivery receipts, read receipts, or per-recipient retry to the send loop — out of scope, unchanged from `post-service-messaging`.
- Not building a general "reports" page — the roster composition count is two numbers added to the existing Relatórios page's KPI grid, not a new page.

## Decisions

**`SELECTED` as a new `audience` string value, with recipient IDs on a new join table, not a JSON column.** `MessageLog.audience` and `MessageRule.audience` are already free-form strings (`VISITOR | MEMBER | ALL`, plus `BIRTHDAY` used only by the birthday scheduler) — no enum type in the DB to migrate, so adding `SELECTED` is a one-line contract change, not a migration. The recipient list itself needs its own table (`MessageLogRecipient { messageLogId, rosterMemberId }`) rather than a JSON array column: it keeps referential integrity with `RosterMember` (a deleted roster member doesn't leave a dangling ID nobody can resolve back to a name), and every other list-shaped relationship in this schema (`MessageRule.logs`, `ServiceTime.messageRules`) is already a real relation, not JSON — staying consistent with the codebase's own pattern beats a shortcut. Alternative considered: store `recipientIds: string[]` directly on `MessageLog` as JSON — rejected because `dispatchMessageSend` already builds recipients from a DB query for every other audience, and a JSON blob would be the only recipient-resolution path that *doesn't* re-verify against current roster state (a `SELECTED` send should still skip someone who got deleted from the roster between pick and send, same as every other audience already effectively does live).

**`recipientIds` only accepted when `audience === "SELECTED"`, validated server-side against the caller's own `crunchId`.** Prevents a `SELECTED` send from being used to smuggle in a roster member ID from a different church. `sendNowSchema` gets a `.refine()` requiring `recipientIds.length > 0` when `audience === "SELECTED"`, mirroring how `ruleCreateSchema` already validates `serviceTimeId` belongs to the same church before accepting it.

**Roster composition report is a live `groupBy`, not a new table or cached counter.** `RosterMember` already has `@@index([crunchId, status])` — `$prismaClient.rosterMember.groupBy({ by: ["status"], where: { crunchId } })` is a single indexed query, cheap at any realistic roster size (dozens to low hundreds, per `post-service-messaging`'s own sizing assumption). No new endpoint needed if `useRoster.ts`'s existing list call can supply this cheaply, but a dedicated `GET /api/church/roster/report` is still worth it so `relatorios.vue` doesn't have to fetch the *entire* roster just to count it — smaller payload, and it composes with the "Público do culto" pattern already on that page as another small KPI card.

**Birthday notify time on `BirthdayMessageSetting`, same `"HH:MM"` string shape as `ServiceTime.time`.** Consistency with the one other place this codebase stores a time-of-day beats inventing a new representation (e.g. minutes-since-midnight as an int). `checkBirthdays`'s `if (now.getHours() < NOTIFY_HOUR) return` — a single global gate before the per-church loop — has to move *inside* that loop, comparing `now` against each church's own `setting.notifyTime` before deciding whether today's occurrence has been handled yet. This is the one real structural change in `birthdayScheduler.ts`: the function currently finds all candidates first and groups by church second; the time gate needs the per-church setting, which today is only loaded (via `upsert`) after grouping — so the gate has to move to *after* the upsert, not before the query. Net effect on churches that never touch this setting: `notifyTime` defaults to `"08:00"`, identical behavior to today.

**`manual-service-end-trigger` extends `ServiceAttendance`, not a new table.** `ServiceAttendance` is already exactly "one row per `serviceTimeId` + `date`" — the record that answers "did this specific occurrence of this service happen, and what do we know about it." Adding `endedAt DateTime?` to it is the smallest change that captures "this occurrence ended, and here's when" without inventing a second concept for the same occurrence. The existing unique constraint (`@@unique([serviceTimeId, date])`) already gives upsert-by-day semantics for free — "Finalizar culto" becomes an upsert of today's row with `endedAt: now()`, independent of whether `visitorCount`/`memberCount` have been filled in yet (both stay optional/zero until someone does the headcount separately, same as today). Alternative considered: a standalone `ServiceOccurrence` table — rejected as duplicating a concept `ServiceAttendance` already owns.

**`computeTargetFireTime` checks for today's `ServiceAttendance.endedAt` first, falls back to `serviceTime.time + offsetMinutes` when absent.** Directly what the user asked for ("pra automação saber qual horário ela deve mandar mensagem"): if a pastor tapped "Finalizar culto" today, the rule fires `offsetMinutes` after that real timestamp instead of the scheduled one; if not, behavior is byte-for-byte what it is today. This requires `checkRules` to query `ServiceAttendance` for `{ serviceTimeId: rule.serviceTimeId, date: <today> }` per rule per tick — one extra indexed lookup (`@@unique([serviceTimeId, date])` doubles as the exact lookup key) per active rule per minute, negligible at this scale.

**"Finalizar culto" button lives next to "Registrar presença" in `relatorios.vue`.** Same screen, same underlying row, same mental model ("stuff about today's service") — a pastor filling in headcount and marking the service over are the same errand, not two different places to visit.

## Risks / Trade-offs

- **[Risk] A `SELECTED` send with a very large hand-picked list defeats the "keep it small, dozens to low hundreds" sizing assumption `post-service-messaging` built the pacing loop around.** → Mitigation: none needed beyond what already exists — the same ~1.5s-per-recipient pacing applies regardless of audience type, so a large `SELECTED` list just takes proportionally longer, exactly like a large `ALL` audience does today.
- **[Risk] Moving the birthday notify-hour gate into the per-church loop means the scheduler now does a church-scoped `upsert` for every church with a birthday today, every tick, before deciding whether to skip.** → Mitigation: this already happens today (the `upsert` already runs before the `lastFiredAt`-based same-day check) — moving the *hour* comparison next to it doesn't add a query, just reorders an existing one relative to a moved `if`.
- **[Risk] A pastor taps "Finalizar culto" accidentally, or twice for the same day.** → Mitigation: upsert-by-day means a second tap just overwrites `endedAt` with a later timestamp — harmless, and arguably correct (the *last* tap is presumably the real end time). An accidental tap on the wrong day isn't distinguishable from a real one; no confirmation dialog proposed here, consistent with how "Registrar presença" itself has no confirmation today.
- **[Trade-off] `SELECTED` sends don't get their own audience-level UI affordance in `MessageRule` (automatic rules) — only in manual send.** Consistent with the Non-Goal above; if a future request wants recurring sends to a fixed hand-picked list, that's a materially different feature (a saved list that persists across weeks) and should be its own change, not bolted on here.

## Migration Plan

- Additive-only migrations, hand-written SQL following `RosterMember`'s/`post-service-messaging`'s pattern (no `prisma migrate dev`):
  1. `ALTER TABLE "BirthdayMessageSetting" ADD COLUMN "notifyTime" TEXT NOT NULL DEFAULT '08:00';`
  2. `ALTER TABLE "ServiceAttendance" ADD COLUMN "endedAt" TIMESTAMP(3);`
  3. New table `MessageLogRecipient` (`id`, `messageLogId` FK → `MessageLog` `onDelete: Cascade`, `rosterMemberId` FK → `RosterMember` `onDelete: Cascade`, indexed on `messageLogId`).
- No backfill needed — every new column/table starts empty or defaulted; existing rows keep working unchanged.
- Rollback: drop `MessageLogRecipient`, drop the two new columns, revert the `SELECTED` audience branch and the `endedAt`-aware branch in `computeTargetFireTime` — no coupling into unrelated existing flows.

## Open Questions

1. **Is `post-service-messaging` the right "Modified Capability" reference, given `openspec/specs/` (the synced/merged directory) only currently contains `prayer-request-moderation`?** This repo's spec-sync discipline appears inconsistent — most shipped changes (including `post-service-messaging` itself) were never synced into the top-level `openspec/specs/`. I followed the codebase's actual behavior (read the real code) rather than the possibly-stale synced-spec state, and placed this change's delta spec at `specs/post-service-messaging/spec.md` to match where `post-service-messaging`'s own spec already lives. Worth running `/opsx:sync` at some point independent of this change, but not blocking it.
2. **Should the roster composition report distinguish `FORMER` (left) roster members, or only count `VISITOR`/`MEMBER` (the two "active" statuses everything else in this feature area already uses)?** Proposed: only the two active statuses, matching `statusesForAudience`'s own `ALL = VISITOR + MEMBER` definition — but confirm with the user, since "quantos membros e quantos visitantes temos" could reasonably be read as "of everyone ever in the roster."
3. **Does "Finalizar culto" need any UI signal that it already ran today** (e.g. showing the recorded time, letting a pastor see/undo it), or is a bare stateless button enough for v1? Proposed: show the recorded `endedAt` time next to the button once set (cheap, avoids "did my tap register?" confusion) — but not building an edit/undo flow beyond re-tapping to overwrite.
4. **Exact placement of the recipient multi-select in "Enviar agora."** Proposed: a third option next to the existing "Público" select (Visitantes / Membros / Todos / **Selecionar pessoas...**) that reveals a roster picker when chosen, reusing the same list `pessoas.vue`'s Rol tab already renders — confirm this matches the user's mental model before implementation starts.
